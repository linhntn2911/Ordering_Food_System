# Implementation Plan: Firebase Data Foundation

**Branch**: `main` | **Date**: 2026-10-17 | **Spec**: `specs/001-food-ordering-system/spec.md`

## Summary

Establish the official FlutterFire connection boundary for the Food Ordering System, define the Firestore schema and security rules, and expose Firebase services through official Riverpod providers. The Flutter client uses Firebase Authentication for identity and Cloud Firestore as the shared database. Firebase project identifiers remain generated by `flutterfire configure`; they are never invented or hand-authored.

## Technical Context

**Language/Version**: Dart `^3.13.2`, Flutter 3.47.x  
**Primary Dependencies**: `firebase_core`, `cloud_firestore`, `firebase_auth`, `flutter_riverpod`, `shared_preferences`  
**Storage**: Cloud Firestore; SharedPreferences for non-sensitive local configuration  
**Testing**: `flutter analyze`, `flutter test`, Firebase Emulator Suite/rules tests when CLI configuration is available  
**Target Platform**: Android first; iOS-compatible Flutter boundary retained

**Performance Goals**: bounded and indexed list queries; real-time order updates under normal connectivity  
**Constraints**: one restaurant, COD only, 8 km delivery radius, no client-owned Admin role or authoritative totals  
**Scale/Scope**: shared foundation for the 23-screen release

## Architecture Decisions

1. `Firebase.initializeApp` runs once during bootstrap using generated `DefaultFirebaseOptions.currentPlatform`.
2. Official Riverpod providers expose `FirebaseAuth` and `FirebaseFirestore` instances after initialization.
3. Feature repositories depend on injected Firebase instances. Widgets never call Firebase SDKs directly.
4. Firestore converters and immutable models map document data at the data boundary.
5. Root collections are `users`, `categories`, `menu_items`, `orders`, `reviews`, and `restaurant_configs`; owner-specific and order-specific data use subcollections.
6. Security rules deny by default and grant the minimum access needed for public menu reads, Customer-owned records, and Admin operations.
7. Order totals, delivery distance, delivery fee, role, and status transitions require trusted validation. Initial client rules intentionally do not claim to replace backend validation.
8. Firebase project ID, API keys, app IDs, and platform configuration are generated by `flutterfire configure` after the project and target platform are selected.

## Configuration Gate

The repository can contain dependencies, schema, rules, providers, and repositories before a cloud project is selected. Runtime connection is complete only after:

1. A Firebase project ID is selected.
2. Android package ID is confirmed; the current value is `com.example.ordering_food_system`.
3. `flutterfire configure` generates `lib/firebase_options.dart` and platform files.
4. Firestore and Email/Password Authentication are enabled in Firebase Console.
5. Rules and indexes are deployed or tested in the emulator.
